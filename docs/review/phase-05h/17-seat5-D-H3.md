## D-H3 (c) — the "asserted to produce denormals" premise (my condition)

**Reading.** Whether the clause closes on a negative probe, and how a direct detector is built. Cue §4.1 (denormals) and §4.5 (name the clock, who owns the FP mode on each thread).

**What the negative probe proves, for me.** From the code (`test_diffuse_gate.cpp` L306–356): it compares IR bits with the caller's FTZ off vs on, guard disabled. Two limits. (1) It sees only a denormal whose flush changes an output bit; a denormal absorbed by a larger addend is invisible. (2) **The FP mode is per thread, and the guard covers only the calling thread.** From the code: `ScopedFlushDenormals` sets MXCSR/FPCR of the thread that constructs it (`Denormals.h` L24–35); the estimator runs its blocks on the process-wide `ThreadPool` (`DiffuseEstimator.cpp` L334, `ThreadPool.cpp` L75–95), whose workers never set FTZ/DAZ (`ThreadPool.cpp`, no guard; `workerLoop` L53–73), while the caller runs a share itself (`runShare` at L89). So in both arms of the probe the worker blocks ran in the workers' inherited mode, and which blocks ran on the caller is decided dynamically (`next_++`). The negative therefore proves: at 16 scene × rate pairs on Linux x86-64 Release, no block of the IR path is denormal-sensitive in a way that reaches the output. It does not prove "no denormal arose", and it does not establish AX37 (5.1) (i)'s intent ("the IR never depends on the host's mode") for the worker share by construction: the workers' mode is whatever the thread that first called `ThreadPool::process()` had (a host thread; Linux `clone` copies the FP state [Hyp]; Windows threads start at the CRT default [Hyp]; macOS unknown). Today that is harmless (the probe); it is a determinism debt (NFR-6 / AX5), not a deadline one: the estimator never runs on the audio thread, and the convolver guards itself per block (`PartitionedConvolver.cpp` L227, `CrossfadingConvolver.cpp` L359, from the code), so the audio-thread denormal CPU risk is covered regardless of this test.

**Platform facts (standard references cited from memory, not from the corpus; each tagged; a calibration step makes the detector self-verifying so the researcher is not needed).**
- **x86-64 (Linux and Windows CI runners, `ci.yml` L92, L94).** MXCSR status flags bits 0–5: IE 0, **DE 1** (a denormal *operand* was consumed; not set when DAZ = 1), ZE 2, OE 3, **UE 4** (a tiny inexact *result*; with FTZ = 1 the result is flushed and UE | PE are set), PE 5; sticky; read/clear from user code with `_mm_getcsr()` / `_mm_setcsr()` on gcc, clang and MSVC x64 — the code already does both on Linux and Windows CI (`Denormals.h` L27–28), so readability is established by the build itself. Source: Intel SDM Vol. 1, MXCSR description (bit layout from memory) [Hyp as to section number]. MSVC also exposes `_statusfp()` / `_SW_DENORMAL` [Hyp]. The x87 status word has its own DE; irrelevant unless `long double` is used (it is not, from the code's double sums).
- **AArch64 (macOS runner `macos-15`, Apple silicon [Hyp: GitHub's default arch]).** FPSR cumulative flags: IOC 0, DZC 1, OFC 2, **UFC 3**, IXC 4, **IDC 7**; readable/clearable at EL0 with `mrs/msr fpsr` (the code already executes `mrs fpcr` at EL0, `Denormals.h` L31). IDC is defined as "an input denormal was flushed because FZ = 1"; with FZ = 0 a denormal input raises no flag, and a tiny inexact result sets UFC. Source: Arm ARM, FPSR / "Input Denormal" [Hyp as to wording]. So the detector on AArch64 is two arms: FZ off → UFC (denormal results arose); FZ on (the guard) → IDC | UFC (something was flushed).
- **MSVC ARM64**: the guard is a no-op and `isSupported()` is false (`Denormals.h` L8, L49–56, from the code); not a CI OS; the FTZ test SKIPs there (L312–313). Note for Phase 13 (Windows-on-ARM users run unguarded).
- **Compilers.** D2 from the code (`src/sim/CMakeLists.txt` L54–57): `/fp:precise` on MSVC, `-ffp-contract=off -fno-fast-math` on gcc/clang. Under `/fp:precise` MSVC does not contract to FMA by default since VS 2022 17.0 (`/fp:contract` off) [Hyp, MSVC docs from memory; the CI runner is VS 2022]. With contraction off and no fast-math, denormal *production* is a property of the IEEE operation sequence and magnitudes, identical across the three compilers up to libm last-ulp differences (the D5 E_target cross-OS check already tolerates 1e-7): a denormal on one OS and not another needs a value within 1 ulp of 2⁻¹⁰²² — negligible [Inferred]. What does differ by platform is the *default mode* of the threads (above), which is the guard's reason to exist.

**The detector (hidden test, three OSes, no `src/sim` change).** Build the probe set with `options.ftzGuard = false` and `options.diffusePool = &ThreadPool(1)` (`Engine.h` L117, from the code; a one-thread pool has no workers, so every block runs on the instrumented thread, and D4 makes the result thread-count independent, so the D5 hashes equal CI's): clear the flags, run, read DE | UE (x86) or UFC then, in the FZ-on arm, IDC | UFC (AArch64); print counts per scene and arm. **Calibrate first** (WI-3): `1e-310 × 1.0` must set DE / (FZ-on) IDC, `1e-300 × 1e-20` must set UE / UFC; if calibration fails the test SKIPs, never passes. Caveat for reading a positive: libm (`exp` of a large negative argument) legitimately produces flushed-or-not zeros that set UE; a positive is localised by running the estimator alone and the synthesis alone (both entry points exist).

## D-H3 (e) — `reset()` may arrive on the audio thread; freeze / offline threading unmeasured

**Reading.** AX38 (i) class (1)'s premise (phase-07 L135–141: the reset sequence "runs on the thread the host calls `reset()` on", "not concurrent with `processBlock`", host contract "not checkable") against file 12 F1/F2/F6 and the code. **(1) Inside or outside my rule?** Inside. My rule is about the *audio clock*, not the function named `processBlock`: "reachable from the callback, including through helpers you did not open" (§4.1), and "treat every entry point as callable from any thread unless the format says otherwise" (CS-3.3). The gate's invariant "never reachable from a real-time `process()`" (debug assert, C3) protects one door while `reset()` and a non-conforming host's `setNonRealtime(true)` (via `processAudio`, F6) open another on the same clock; it protects the audio thread only if those two are also kept off it.
